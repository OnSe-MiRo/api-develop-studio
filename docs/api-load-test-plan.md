# API 부하테스트 계획

## 1. 목적

API Develop Studio 백엔드가 예상 동시 사용량에서 안정적으로 동작하는지 확인하고, 조회·저장·실행 경로별 처리 한계와 병목을 찾는다.

이 계획은 다음 질문에 답하는 것을 목표로 한다.

- 일반 조회 요청의 처리량과 응답 시간은 어느 수준인가?
- SQLite 기반 문서 저장이 동시 요청에서도 정상적으로 직렬화되는가?
- 같은 문서를 동시에 수정할 때 낙관적 잠금이 데이터 손상 없이 `409`로 충돌을 알리는가?
- `/api/run`이 만드는 하위 프로세스가 동시 실행될 때 서버 자원이 고갈되지 않는가?
- 부하가 제거된 뒤 오류율과 응답 시간이 정상 수준으로 회복되는가?

## 2. 범위

### 포함

| 분류 | 엔드포인트 | 확인할 특성 |
| --- | --- | --- |
| 상태 확인 | `GET /example-api/health` | HTTP 서버 자체의 최소 비용 기준선 |
| 목록 조회 | `GET /api/projects`, `GET /api/cases?project=example-api.json`, `GET /api/pipelines?project=example-api.json` | SQLite 조회와 JSON 응답 |
| 단건 조회 | `GET /api/projects/{reference}`, `GET /api/cases/{reference}` | 문서와 리비전 메타데이터 조회 |
| 리비전 조회 | `GET /api/cases/{reference}/revisions` | 리비전 수 증가에 따른 조회 성능 |
| 문서 저장 | `PUT /api/cases/{reference}` | SQLite 쓰기, JSON 파일 투영, 낙관적 잠금 |
| 케이스 실행 | `POST /api/run` | Python 하위 프로세스 생성과 대상 API 호출 |
| 오류 경로 | 잘못된 reference, 오래된 revision, 잘못된 payload | `400`·`409` 응답의 안정성 |

### 제외

- `POST /api/generate`: Java 기반 OpenAPI Generator 성능은 별도 용량 계획 대상으로 다룬다.
- 외부 OpenAPI URL을 읽는 `POST /api/docs`: 외부 네트워크 지연이 결과를 왜곡하므로 첫 단계에서 제외한다.
- 파일 업로드: 25 MB 경계와 디스크 처리량은 별도의 대용량 업로드 테스트로 분리한다.
- React 정적 파일과 브라우저 렌더링 성능
- 외부 API 자체의 성능 평가

## 3. 테스트 원칙과 안전장치

- 운영 환경과 운영 데이터에는 실행하지 않는다. 별도 데이터베이스와 `case/`, `projects/`, `pipelines/`, `logs/` 볼륨을 사용한다.
- 부하 발생기는 대상 서버와 다른 호스트에서 실행한다. 같은 호스트를 사용할 때는 결과에 한계를 명시한다.
- 실행 전 기능 테스트를 통과시키고 테스트 데이터의 스냅샷을 보관한다.
- 저장 테스트 reference는 `load-test/{worker-id}/{sequence}.json`처럼 테스트 전용 경로를 사용한다.
- 보안 변수, 실제 API 키와 개인정보는 fixture 또는 결과 로그에 넣지 않는다.
- 실패율이나 자원 사용량이 중단 조건을 넘으면 즉시 부하 증가를 멈춘다.
- 결과 비교 시 애플리케이션 버전, 커밋, OS, CPU, 메모리, 디스크, Python 버전과 실행 방식을 함께 기록한다.

## 4. 도구와 계측

부하 발생 도구는 k6를 우선 사용한다. 시나리오별 가상 사용자, 단계적 부하, 임계값, JSON 결과 출력을 한 스크립트에서 관리하기 쉽고 대상 애플리케이션에 런타임 의존성을 추가하지 않기 때문이다.

최소 수집 항목은 다음과 같다.

- 클라이언트: 요청 수, RPS, 동시 사용자 수, p50·p90·p95·p99 응답 시간, 네트워크 오류율, HTTP 상태별 건수
- 서버 프로세스: CPU, RSS 메모리, thread 수, 열린 파일 또는 handle 수, 하위 프로세스 수
- 저장소: `studio.db` 크기, WAL 크기, 디스크 IOPS·지연, `database is locked` 오류 수
- 애플리케이션: `400`, `409`, `5xx`, timeout 건수와 `/api/run`의 `exitCode != 0` 건수

가능하면 Docker 통계 또는 운영 환경의 표준 모니터링을 5초 간격으로 수집한다. 클라이언트 결과와 서버 로그는 같은 시간대로 맞춘다.

## 5. 테스트 데이터

재현 가능한 전용 fixture를 준비한다.

| 데이터셋 | 규모 | 용도 |
| --- | ---: | --- |
| Small | 프로젝트 1, 케이스 10, 파이프라인 2 | 기능 확인과 smoke |
| Medium | 프로젝트 20, 케이스 2,000, 파이프라인 100 | 일반 부하와 목표 용량 검증 |
| Large | 프로젝트 100, 케이스 20,000, 각 케이스 리비전 최대 100 | 목록·리비전 조회의 확장성 탐색 |

본문 크기는 1 KB, 10 KB, 100 KB 세 구간으로 나눈다. 읽기 요청은 특정 문서에만 캐시 효과가 몰리지 않도록 reference를 무작위로 선택하되, 실행마다 같은 seed를 사용한다.

`PUT` 시나리오는 다음 두 종류를 반드시 분리한다.

1. 고유 문서 저장: 가상 사용자마다 다른 reference를 써서 순수 쓰기 처리량을 측정한다.
2. 동일 문서 경합: 모든 사용자가 같은 revision을 기준으로 같은 문서를 갱신한다. 최초 성공 이외의 `409`는 예상 결과이며 `5xx`, 손실된 리비전 또는 깨진 JSON이 실패다.

## 6. 부하 모델

초기 목표 동시 사용량이 정해지지 않았으므로 아래 값으로 기준선을 만든 뒤 실제 사용자 수와 트래픽 자료에 맞춰 조정한다.

| 단계 | 부하 | 시간 | 목적 |
| --- | --- | ---: | --- |
| Smoke | 엔드포인트별 1 VU | 1분 | 스크립트와 응답 검증 |
| Baseline | 5 VU, 읽기 중심 | 5분 | 무부하 대비 기준선 |
| Target | 20 → 50 VU | 단계별 10분 | 초기 목표 용량 확인 |
| Stress | 50부터 25 VU씩 증가 | 단계별 5분 | 처리 한계와 포화 지점 탐색 |
| Spike | 5 → 100 → 5 VU | 상승 30초, 유지 2분, 회복 5분 | 급증 대응과 회복 확인 |
| Soak | Target 부하의 70% | 2시간 | 메모리·thread·WAL·로그 누적 확인 |

Target 혼합 트래픽은 실제 자료가 생기기 전까지 다음 비율을 사용한다.

- 목록 조회 35%
- 단건 문서 조회 35%
- 리비전 조회 10%
- 고유 문서 저장 10%
- 동일 문서 경합 5%
- `/api/run` 5%

`/api/run`은 요청마다 하위 프로세스를 만들기 때문에 읽기 부하와 별도 시나리오도 수행한다. 동시 실행 수를 1, 2, 5, 10 순서로 올리고 각 단계에서 프로세스 수, 메모리와 응답 시간을 확인한다. 호출 대상은 외부 서비스가 아닌 내장 예제 API 또는 지연을 제어할 수 있는 stub을 사용한다.

## 7. 시나리오

### A. 읽기 기준선

1. `GET /example-api/health`로 HTTP 처리 오버헤드를 측정한다.
2. Small, Medium, Large 데이터셋에서 목록과 단건 조회를 각각 실행한다.
3. 데이터 규모별 p95와 RPS 변화를 비교해 선형 이상으로 악화되는 구간을 찾는다.

### B. 혼합 사용 흐름

사용자 한 명의 흐름을 `프로젝트 목록 → 케이스 목록 → 케이스 조회 → 리비전 조회`로 구성한다. 요청 사이에 1~3초의 think time을 넣고 Target, Stress, Spike, Soak 단계를 수행한다.

### C. 고유 문서 동시 저장

각 가상 사용자가 서로 다른 케이스를 생성하고, 응답의 `_storage.revision`을 사용해 3회 수정한다. 모든 성공 응답 이후 다음을 검증한다.

- 최종 revision이 예상값과 일치한다.
- SQLite 최신 내용과 `case/` JSON 투영본이 일치한다.
- JSON 파일이 부분 기록되거나 손상되지 않았다.
- `5xx`와 `database is locked` 오류가 없다.

### D. 동일 문서 경합

동일한 `_storage.revision`으로 5, 20, 50개 요청을 동시에 보낸다. 한 요청만 성공하고 나머지는 현재 revision이 포함된 `409`를 받아야 한다. 테스트 종료 후 리비전이 성공 건수만큼만 증가했는지 확인한다.

### E. 케이스 실행

저장된 `example/users/get_user.json`을 `/api/run`으로 실행한다. 동시 실행 수를 점진적으로 높이고 다음을 확인한다.

- HTTP 응답은 `200`이며 결과의 `exitCode`가 `0`이다.
- 하위 프로세스가 요청 종료 후 남지 않는다.
- timeout 이후에도 thread와 임시 디렉터리가 정리된다.
- 읽기 API를 함께 호출했을 때 응답 시간이 허용 범위 안에 있다.

### F. 장애와 회복

제어 가능한 stub에 지연과 오류를 주입해 `/api/run`의 timeout 경로를 확인한다. Stress 또는 Spike 종료 후 5분 동안 Baseline 부하를 보내 p95, 오류율, 메모리와 하위 프로세스 수가 이전 기준 수준으로 회복되는지 확인한다.

## 8. 초기 통과 기준

서비스 SLO가 아직 없다는 전제의 임시 기준이다. 첫 Baseline 결과와 실제 사용량이 확보되면 수치를 승인받아 확정한다.

| 항목 | 초기 기준 |
| --- | --- |
| 일반 읽기 p95 | Target 부하에서 300 ms 이하 |
| 일반 읽기 p99 | Target 부하에서 1초 이하 |
| 고유 문서 저장 p95 | Target 부하에서 1초 이하 |
| 비예상 오류율 | 전체 요청의 1% 미만 |
| 서버 오류 | 정상 입력에서 `5xx` 0건 |
| 경합 정확성 | 예상 `409` 외 오류 0건, revision 유실 0건 |
| `/api/run` 정확성 | 성공 대상의 `exitCode != 0` 0건, 고아 프로세스 0건 |
| 자원 | CPU 85% 또는 메모리 80% 초과 상태가 5분 이상 지속되지 않음 |
| 회복 | Spike 종료 후 5분 안에 p95와 자원이 Baseline의 120% 이내로 복귀 |
| Soak | 2시간 동안 메모리, thread, WAL이 지속적으로 증가하지 않음 |

Stress 테스트의 최대 처리량은 위 기준을 처음 위반하기 직전 단계의 안정 RPS로 기록한다. `/api/run`의 용량은 전체 RPS가 아니라 안정적인 최대 동시 실행 수로 별도 기록한다.

## 9. 중단 조건

다음 중 하나가 발생하면 해당 단계의 부하 증가를 중단하고 증거를 보존한다.

- 1분 이동 구간의 `5xx` 또는 네트워크 오류율이 5%를 초과한다.
- 대상 CPU가 95% 또는 메모리가 90%를 2분 이상 유지한다.
- SQLite 손상, JSON 투영본 불일치 또는 예상하지 않은 revision 유실이 발견된다.
- 하위 프로세스 수가 요청 완료 뒤에도 계속 증가한다.
- 대상 호스트가 응답하지 않거나 운영 안정성에 영향을 줄 가능성이 있다.

## 10. 실행 순서

1. 테스트 브랜치와 전용 환경을 준비하고 애플리케이션 버전 및 호스트 사양을 기록한다.
2. 전체 Python 테스트를 실행하고 실패가 없음을 확인한다.
3. Small, Medium, Large fixture를 생성하고 데이터 건수와 크기를 검증한다.
4. k6 스크립트에 응답 body와 상태 코드 검증을 구현한다.
5. Smoke를 통과시킨 뒤 읽기 Baseline을 3회 실행한다.
6. Target 혼합 부하를 3회 실행하고 중앙값을 기준 결과로 사용한다.
7. 고유 문서 저장과 동일 문서 경합을 별도로 실행하고 저장 무결성을 검사한다.
8. `/api/run`의 최대 안정 동시 실행 수를 별도로 측정한다.
9. Stress, Spike, Soak 순서로 수행하며 단계 사이에 자원이 기준선으로 회복될 시간을 둔다.
10. 결과를 이전 기준선과 비교하고 병목, 재현 방법, 개선 우선순위를 보고한다.

## 11. 산출물과 완료 조건

실행별로 다음 파일을 보관한다.

- 부하 스크립트와 사용한 fixture 생성 스크립트
- k6 원본 결과와 요약 보고서
- 서버 자원 지표와 애플리케이션 로그
- 테스트 환경·버전·명령·시작 및 종료 시각
- 데이터 무결성 검사 결과
- 최대 안정 RPS, `/api/run` 최대 안정 동시 실행 수와 최초 실패 지점

계획 완료 조건은 Smoke부터 Soak까지 재현 가능한 명령이 준비되고, 초기 통과 기준의 각 항목에 측정값 또는 명확한 실패 원인이 채워진 상태다. 기준을 넘지 못하면 병목을 코드 경로, SQLite, 파일 I/O, 하위 프로세스 또는 테스트 환경 중 하나로 좁혀 후속 작업을 등록한다.

## 12. 결과 대시보드 개발 계획

### 12.1 목표와 1차 범위

부하테스트 실행 결과를 프로젝트와 시나리오별로 보관하고, 한 번의 실행 결과와 이전 실행 대비 변화를 웹에서 빠르게 판단할 수 있게 한다.

1차 버전은 완료된 테스트 결과의 가져오기와 분석에 집중한다. 웹에서 k6 프로세스를 시작·중지하는 기능, 실시간 스트리밍, 알림 전송과 외부 모니터링 연동은 후속 범위로 둔다. 이렇게 하면 임의 명령 실행과 장시간 작업 관리 문제를 먼저 도입하지 않고 결과 데이터 계약과 판단 화면을 안정화할 수 있다.

### 12.2 사용자 흐름

1. 사용자가 k6 테스트를 실행해 요약 파일과 시간 구간별 집계 파일을 생성한다.
2. 결과 가져오기 명령으로 실행 메타데이터와 집계값을 서버에 등록한다.
3. 웹 상단의 `부하테스트` 메뉴에서 프로젝트, 시나리오, 기간과 성공 여부로 실행 목록을 필터링한다.
4. 실행을 선택해 핵심 지표, 시간 추이, 엔드포인트별 결과와 통과 기준을 확인한다.
5. 기준 실행과 비교 실행을 선택해 응답 시간, 처리량과 오류율의 차이를 확인한다.

### 12.3 결과 데이터 계약

k6 원본 이벤트 전체는 크기가 빠르게 증가하므로 대시보드 요청 시 직접 읽지 않는다. 테스트 종료 후 importer가 원본을 순차 처리해 5초 또는 10초 구간의 집계 데이터와 최종 요약을 만든다.

결과 bundle의 최상위 구조는 다음처럼 정의한다.

```json
{
  "schemaVersion": 1,
  "run": {
    "id": "run_20260907_120000_ab12cd",
    "project": "example-api.json",
    "scenario": "target-mixed",
    "startedAt": "2026-09-07T12:00:00Z",
    "endedAt": "2026-09-07T12:20:00Z",
    "status": "passed",
    "appVersion": "1.0.1",
    "commitSha": "abcdef1",
    "environment": {
      "os": "linux",
      "cpu": "4 vCPU",
      "memoryMb": 8192,
      "executionMode": "docker-compose"
    }
  },
  "summary": {
    "requests": 120000,
    "rps": 100,
    "errorRate": 0.001,
    "latencyMs": {"p50": 42, "p90": 120, "p95": 180, "p99": 420, "max": 980},
    "vusMax": 50,
    "thresholdsPassed": true
  },
  "thresholds": [],
  "endpointMetrics": [],
  "series": []
}
```

시간, 비율과 latency 단위는 각각 UTC ISO 8601, `0~1`, millisecond로 고정한다. endpoint는 동적 ID를 제거한 정규화 이름을 사용하고 URL query와 header의 비밀값은 저장하지 않는다. 알 수 없는 필드는 허용하되 `schemaVersion`이 지원 범위를 벗어나면 가져오기를 거부한다.

### 12.4 저장 구조

기존 문서 리비전 테이블과 수명주기가 다르므로 부하테스트 전용 테이블을 `studio.db`에 추가한다.

| 테이블 | 주요 필드 | 역할 |
| --- | --- | --- |
| `load_test_runs` | id, project_reference, scenario, status, started_at, ended_at, app_version, commit_sha, environment_json, summary_json | 실행 목록과 최종 요약 |
| `load_test_thresholds` | run_id, metric, condition, actual_value, passed | 통과 기준별 결과 |
| `load_test_endpoint_metrics` | run_id, method, endpoint, request_count, error_rate, p50_ms, p90_ms, p95_ms, p99_ms, max_ms | 엔드포인트별 비교 |
| `load_test_series` | run_id, bucket_at, rps, active_vus, error_rate, p95_ms, cpu_percent, memory_mb, child_processes | 시간 추이 차트 |

외래 키와 `(run_id, bucket_at)` 및 목록 필터용 `(project_reference, started_at DESC)` 인덱스를 둔다. 가져오기는 하나의 transaction으로 처리해 일부 데이터만 보이는 상태를 막는다. 동일 run id 재등록은 기본적으로 `409`를 반환하고 명시적인 교체 동작은 1차 범위에서 제공하지 않는다.

원본 k6 결과와 서버 로그는 `data/load-tests/{run-id}/`에 보관하되 API 목록 응답에는 포함하지 않는다. 기본 보존 기간은 30일로 제안하며, 자동 삭제를 도입하기 전에는 관리 명령이 삭제 대상을 먼저 출력하고 확인 후 제거하도록 한다.

### 12.5 백엔드 API

| Method | 경로 | 설명 |
| --- | --- | --- |
| `POST` | `/api/load-tests/runs` | 정규화된 결과 bundle 검증 및 저장 |
| `GET` | `/api/load-tests/runs` | 프로젝트, 시나리오, 상태, 기간 기반 목록과 pagination |
| `GET` | `/api/load-tests/runs/{id}` | 실행 요약, threshold와 endpoint 집계 조회 |
| `GET` | `/api/load-tests/runs/{id}/series` | 구간과 해상도를 지정한 시간 추이 조회 |
| `GET` | `/api/load-tests/compare?baseline={id}&candidate={id}` | 두 실행의 절대값·증감률 비교 |

목록 API는 `limit`과 opaque cursor를 사용하고 기본 20건, 최대 100건으로 제한한다. series API는 화면 폭에 맞는 최대 point 수를 받아 서버에서 추가 집계해 반환한다. 가져오기 body 크기와 series point 수에 상한을 두고 숫자의 `NaN`, 무한대, 음수 latency와 잘못된 비율을 거부한다.

비교 API는 같은 `schemaVersion`과 같은 시나리오의 실행을 기본 허용 조건으로 삼는다. 다른 환경이나 VU 설정을 비교하면 차단하지는 않지만 화면에 `비교 조건 다름` 경고를 표시할 수 있는 metadata를 반환한다.

### 12.6 화면 구성

라우터에 `/load-tests`와 `/load-tests/results?run={id}`를 추가하고 상단 메뉴에 `부하테스트`를 배치한다.

#### 실행 목록

- 프로젝트, 시나리오, 상태, 실행 기간 필터
- 실행 시각, app version 또는 commit, 최대 VU, RPS, p95, 오류율, threshold 통과 여부
- 최신 결과와 직전 동일 시나리오 대비 p95·오류율 변화 표시
- 결과 없음, 로딩, API 오류와 부분 데이터 상태

#### 실행 상세

- 요약 카드: 통과 여부, 요청 수, RPS, 최대 VU, p50·p95·p99, 오류율
- 시간 추이: RPS, p95, 오류율, VU와 서버 CPU·메모리
- endpoint 표: method, 정규화 endpoint, 요청 수, p95, p99, 오류율, 상태
- threshold 표: 조건, 실측값, 통과 여부
- 실행 환경: 버전, commit, OS, CPU, 메모리, 시작·종료 시각
- 중단 조건 발생 시점과 importer 경고

#### 실행 비교

- 기준 실행과 비교 실행 선택
- 핵심 지표의 절대 차이와 증감률
- endpoint별 p95·오류율 regression 정렬
- 두 실행의 시간 추이 겹쳐 보기
- 환경, 데이터셋, 시나리오 또는 최대 VU가 다를 때 비교 주의 표시

차트는 1차 버전에서 번들 크기와 유지보수 비용을 평가한 뒤 선택한다. 외부 차트 라이브러리를 도입한다면 버전을 고정하고 접근성, responsive layout과 tooltip keyboard 접근을 확인한다. 의존성을 추가하지 않는 경우에는 작은 SVG line chart와 의미가 동일한 표를 함께 제공한다. 성공과 실패는 색상만으로 구분하지 않고 아이콘과 텍스트를 함께 사용한다.

### 12.7 구현 단계

#### 1단계: 계약과 importer

- JSON schema와 정상·오류 fixture 작성
- k6 `handleSummary` 및 원본 출력에서 bundle을 생성하는 importer 구현
- secret 제거, endpoint 정규화와 시간 bucket 집계 검증
- 같은 입력으로 항상 같은 집계가 만들어지는 단위 테스트 추가

완료 기준: Smoke와 Target 예제 결과가 schema validation을 통과하고 수작업 계산과 요청 수, p95, 오류율이 일치한다.

#### 2단계: 저장소와 조회 API

- DB migration과 전용 repository 구현
- atomic import, 중복 run, pagination, filter, 상세 및 series API 구현
- 잘못된 수치, 과대 body, 존재하지 않는 run과 비교 불가 조건 테스트
- 기존 문서 저장과 동시에 사용할 때 SQLite lock 회귀 테스트

완료 기준: 백엔드 정상·오류·경계 테스트가 통과하고 20,000개 run metadata에서 목록 조회 계획과 응답 시간이 허용 범위에 든다.

#### 3단계: 대시보드 MVP

- 라우터, 상단 메뉴, 목록, 상세 화면 구현
- 요약 카드, threshold, endpoint 표와 시간 추이 차트 구현
- URL query에 필터와 선택 run을 반영해 새로고침과 공유가 가능하게 처리
- loading, empty, error, mobile layout과 keyboard 탐색 확인

완료 기준: 사용자가 예제 결과를 찾아 상세 지표와 실패 threshold를 확인할 수 있고 `npm run build`가 통과한다.

#### 4단계: 비교와 회귀 판정

- 같은 프로젝트·시나리오의 이전 실행 자동 추천
- 지표 및 endpoint별 증감률과 regression 표시
- 임시 통과 기준과 사용자 지정 threshold를 함께 표시
- 비교 조건 불일치 경고 구현

완료 기준: 기준·비교 실행의 원본 요약으로 계산한 값과 화면 증감률이 일치하고, regression endpoint를 p95 악화순으로 찾을 수 있다.

#### 5단계: 운영 보강

- 대량 series downsampling과 API 응답 크기 제한
- 보존 기간 점검·정리 명령, 백업과 복구 절차
- 대시보드 자체의 목록·상세 API 부하테스트
- 사용자 문서, 데이터 형식과 백엔드 API 문서 갱신

완료 기준: 30일 예상 데이터에서 조회 성능 기준을 만족하고 정리 전후 참조 무결성과 복구 절차를 검증한다.

### 12.8 대시보드 품질 기준

| 항목 | 기준 |
| --- | --- |
| 목록 응답 | 20,000개 run metadata에서 p95 500 ms 이하 |
| 상세 응답 | endpoint 500개, series 2,000 point 기준 p95 1초 이하 |
| 화면 표시 | 일반 개발 PC에서 API 응답 후 1초 안에 주요 요약 표시 |
| 정확성 | importer, API와 화면 표시의 요청 수·percentile·오류율 일치 |
| 안정성 | 불완전한 bundle이 저장되지 않고 원인을 포함한 `400` 반환 |
| 접근성 | keyboard 탐색 가능, 상태를 색상 외 텍스트로도 제공 |
| 회귀 방지 | Python 테스트와 frontend 데이터 변환·화면 테스트 통과 |

수치는 첫 구현의 임시 기준이며 실제 결과 크기와 배포 환경을 측정한 뒤 확정한다.

### 12.9 검증 계획

- Python: migration, repository, importer, API 정상·오류·경계 조건 단위 테스트
- 데이터: 고정 fixture로 percentile, rate, bucket과 비교 증감률 golden test
- React: router, filter, loading·empty·error, KPI 및 표 렌더링 테스트
- 통합: k6 예제 실행 → importer → API 조회 → 대시보드 표시 흐름
- 성능: run 20,000개와 series 2,000 point fixture로 목록·상세 응답 측정
- 수동 QA: desktop·좁은 화면, 긴 endpoint, 큰 수치, threshold 실패, 조건이 다른 실행 비교
- 최종 검증: `python3 -m unittest discover -s tests -v`, frontend test 명령과 `web/`의 `npm run build`

대시보드 개발 완료 조건은 테스트 결과를 재현 가능하게 가져오고, 목록·상세·비교 화면의 수치가 원본과 일치하며, 보존·오류·접근성·성능 기준과 관련 자동화 검증을 모두 만족한 상태다.

## 13. 진행 상황 기록 규칙

이 계획에 따른 모든 구현과 테스트 진행 상황은 [`API 부하테스트 및 대시보드 개발 진행 기록`](api-load-test-progress.md)에 남긴다. 해당 문서를 작업 상태의 단일 기준으로 사용하며 코드 변경과 진행 기록 갱신을 같은 작업 범위에 포함한다.

- 작업 시작 전 해당 단계 상태를 `진행`으로 바꾸고 목표, 예정 파일과 시작 시각을 기록한다.
- 구현 범위나 설계 판단이 달라지면 결정, 이유와 영향을 기록한다.
- 의미 있는 구현 단위가 끝날 때 변경 파일, 현재 결과와 다음 작업을 기록한다.
- 테스트 명령과 성공·실패 결과를 모두 기록한다.
- 차단 사유와 시도한 해결책을 기록하고 해소 뒤에도 이력을 보존한다.
- 단계 완료 기준과 검증을 충족한 경우에만 `완료`로 변경한다.
- 사용자에게 완료를 보고하기 전에 현재 요약, 단계 상태, 검증 기록과 변경 이력을 최종 갱신한다.

진행 기록 자체가 누락된 작업은 해당 구현 단계가 완료되지 않은 것으로 간주한다.
