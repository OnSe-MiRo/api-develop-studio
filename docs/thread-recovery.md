# 로컬 요청 스레드 회복 검증

기준 `develop 654515d`의 이전 35 VU 시험은 부하 구간을 완주했으며, 사후 5분 평균 스레드 2.58→4.00으로 120% 회복 기준을 넘었다. [이전 기록](case-list-recovery.md)

실제 HTTP 요청 6개를 동시에 처리하고 유휴 상태로 두는 회귀에서, 기존 AnyIO 요청 worker 6개가 11초 뒤에도 살아 있었다. AnyIO는 새 요청을 배치할 때 유휴 worker를 정리한다. 새 앱별 요청 풀은 worker 최대 40개와 기존 AnyIO 호출 admission을 사용하며 1초 동안 대기 작업이 없는 worker를 종료한다. 정상 요청에 이어 예상 409를 반환하는 회귀에서는 동기 오류 응답 함수가 별도의 AnyIO worker를 남겼다. JSON 오류 응답을 async handler로 등록해 이 경로를 정리했다.

요청 풀은 각 작업에 인증 ContextVar를 복사한다. 취소된 호출의 실제 작업이 끝날 때까지 admission을 유지하고, 종료는 대기 작업 처리·취소와 실행 작업 완료를 기다린다. 함수 예외와 스레드 시작 실패 뒤에도 대기 상태를 정리한다. 작업 실행용 `JobManager`와 HTTP 요청 처리 풀은 각각의 수명주기를 갖는다. 사용자별 작업 조회와 실행 슬롯 정책은 [실행 안내](async-runs.md)를 따른다.

검증은 격리된 SQLite Medium 스냅샷에서 실제 loopback HTTP로 수행한다. 기본 35 VU·7,200초 profile과 같은 서버의 전후 5 VU·300초 기준선을 비교하고, 원래의 오류·부하 중단 조건과 120% 회복 기준을 적용한다. 스레드 이름·native ID는 진단용 loopback 공급자에서만 수집한다. P1의 v1·v2 지문으로 측정한 과거 결과를 재현하며 새 측정은 요청 풀 소스를 포함한 v3 지문을 요구한다.
