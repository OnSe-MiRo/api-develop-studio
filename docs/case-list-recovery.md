# 전체 케이스 목록과 장시간 부하 후 회복

기준 커밋은 `ef0764cf04b6f88695f6b9f9456423dc129e9769`, 수정 후보는 `8f28e9afa982af0d61ceb42b11906b93e143d045`다. 이전 시험에서 쓰기 뒤 케이스가 늘면서 전체 목록 p95가 62.83→138.83ms, 사후 읽기 p95가 46.89→95.94ms가 됐다. 서버 CPU도 기준선의 165.8%였다. [이전 검증](sync-run-admission-validation.md)

실제 35 VU·2시간 부하를 완주하고 같은 서버의 사후 5분을 측정했다. 읽기 p95와 CPU 회복 기준은 통과했다. 평균 스레드 수 회복 기준에 실패해 캠페인 종합 판정은 `failed`다. [기계 판독 결과](case-list-recovery.json)

## API와 회귀

페이지 조건을 생략한 `GET /api/cases`는 정렬된 `items`와 기존 `details.url`을 반환한다. POSIX의 SQLite 경로에서는 Workspace별 실제 파일 경로와 변경 정보를 확인해 반복 파일 읽기를 줄인다. 파일 교체·직접 수정·삭제, 늦게 끝난 동시 읽기, 캐시 용량, 다른 Workspace의 같은 참조와 심볼릭 링크 차단을 검사했다. 긴 URL과 자격 증명 후보의 반환값은 보존하고 캐시에는 보관하지 않는다. Windows에서는 파일을 직접 읽고, PostgreSQL에서는 저장 리비전을 사용한다. [세부 동작](case-list-pagination.md)

최종 후보에서 PostgreSQL·Redis가 포함된 전체 Python 730개, 프런트엔드 169개(38파일), production build, 생성 서버·LT-5 및 이전 P1 보고서 최신성, k6 모델 5개가 통과했다. 첫 후보의 P1 재생성 실패는 이전 28개 소스 지문과 새 지문 집합을 구분해 수정했다. build에는 기존 번들 크기 경고가 있었다.

## 측정 방법

- 이전 측정과 같은 8논리코어 macOS에서 k6 2.3.0과 SQLite Studio를 사용했다. Medium은 프로젝트 20개·케이스 2,000개·파이프라인 100개, seed 20260929, 원본 SHA-256은 `a83c873f2f2961b7a7e20eb7a04a8aa7c4ae5cf781385270d6dcfb49181702a9`다.
- 실제 HTTP 비교에는 기준과 후보 각각의 격리 서버 및 동일한 스냅샷의 복사본을 사용했다. 파일 변경 시각이 안정된 뒤 필터 없는 첫 전체 조회와 반복 조회 2회를 측정했다. 이어 프로젝트당 1회 예열, 3회 측정을 실시하고 각 쌍의 호출 순서를 교차했다. 응답 전체 바이트의 일치를 확인했다. 아래 시간은 클라이언트에서 본 값이다.
- 새 정규 부하는 호스트의 1분 load average ≤12, 5분 값 ≤16이 60초 유지된 뒤 시작했다. Target은 기본 20→50 VU 각 600초, Soak는 독립 Medium 스냅샷으로 35 VU·7,200초와 같은 서버에서 전후 5 VU·300초씩이다. k6 요청·중단·시간 제한은 이전 시험과 같다.
- P1의 별도 25초 진단에서는 예열을 포함한 케이스 목록 요청 40건, 참조 4,000개 중 실제 JSON 내용 읽기가 1,000건이었다. 30개 목록 요청은 파일 내용 읽기 0회였다. P1 추적은 실제 URL 요약 로더를 통과하고, 원문이나 URL 대신 시간·건수·바이트를 기록한다.

각 데이터에서 20개 프로젝트의 반복 조회를 60쌍씩 대조했고 응답 전체 바이트가 일치했다.

## 정규 부하와 회복

- 20→50 VU 각 10분 Target은 통과했다. 전체 HTTP 23,750건 중 동기 실행 1,166건이 모두 200이었고 DB의 고유 성공 Run ID 수와 일치했다. 예상 충돌은 992건, 예기치 않은 오류율은 0이었다.
- 35 VU profile은 2시간을 완주했다. 활성 VU 표본 7,200개가 7,198.99초에 걸쳐 수집됐다. 전체 142,746건 중 200은 137,026건, 예상 409는 5,720건이었다. 동기 실행은 7,073건 모두 200·고유 Run ID·exit 0이었다. 429·예기치 않은 오류·실행 실패는 0건이었다.
- 부하 구간 읽기 p95 11.19ms·p99 17.64ms, 동기 run p95 165.63ms였다. 사전·부하·사후 각 phase의 원본·리비전·투영 무결성이 통과했고 종료 후 자식 프로세스·임시 파일은 0개였다. 재사용한 원본 Medium fixture의 최종 검증 결과도 생성 당시와 같았다.
