# 동기 실행 429와 로컬 목표 부하 재검증

최종 후보에서 기본 20→50 VU Target 3회와 35 VU·2시간 부하 구간을 모두 완주했다. 합계 10,538건의 동기 실행은 전부 HTTP 200·고유 성공 Run ID로 확인했고 동기 429는 0건이었다. 35 VU 캠페인의 종합 판정은 사후 회복 기준 미달로 실패다. [구조화한 측정 결과](sync-run-admission-validation.json)

## 수정과 검증 조건

기준은 로컬 `develop`의 `a767652`, 최종 검증 후보는 `b83e3f5ba5e0a79ddfec3e2e52495db10f61b75d`이다. 기본 worker 두 개가 모두 사용 중이면 `POST /api/run`은 같은 HTTP 요청에서 빈 슬롯을 기다린다. 슬롯을 얻은 요청은 한 번만 실행한다. 기본 대기 인원은 프로세스 전체 16건, 대기 시간은 6초다. 포화·시간 초과 시 기존 429 의미를 보존하고 종료 중인 대기에는 503을 반환한다. 설정과 비동기 작업의 접수 계약은 [실행 안내](async-runs.md)에 있다.

평문 SQLite 케이스용 자식 프로세스가 시작될 때 PostgreSQL 오류 클래스와 Fernet을 미리 불러오던 비용도 줄였다. PostgreSQL 오류 처리 및 실제 암복호화를 사용할 때 기존 구현을 로드한다. 같은 loopback GET을 두 후보의 실제 자식 runner로 번갈아 실행해 한 번씩 예열하고 12쌍을 측정했다. 높은 호스트 부하에서 프로세스 시작부터 정상 종료까지의 중앙값은 3,467.3→1,595.8ms였다.

기존 [출시 후보 기록](local-release-validation.md)과 동일한 Medium SQLite fixture와 macOS arm64 k6 2.3.0을 사용했다. 프로젝트 20개·케이스 2,000개·파이프라인 100개, 리비전 깊이 1, seed 20260929다. fixture SHA-256은 `a83c873f2f2961b7a7e20eb7a04a8aa7c4ae5cf781385270d6dcfb49181702a9`, k6 바이너리 SHA-256은 `efb8282e24ffe18f54ce3679eaa71d72e0645bbb97b14e2a05cc8b192abf48e3`이다.

- 정규 Target은 20 VU와 50 VU 각 600초다. Soak는 35 VU·7,200초이며 같은 서버에서 전후 5 VU 읽기를 각 300초 수행한다. 각 실행은 새로운 합성 DB 스냅샷을 사용하고 k6는 실제 loopback HTTP로 호출한다.
- 혼합 비율, 5초 일반 요청 timeout·10초 동기 실행 timeout, 원래 k6 check·중단·무결성 조건을 사용했다. 워크로드와 중단 코드가 기준 커밋과 같은지 확인했다. 의도한 revision 충돌 409는 검증된 승자·리비전과 함께 집계한다.
- 호스트 간섭 관측 후 최종 후보는 8논리코어 Mac의 1분 load average ≤12, 5분 값 ≤16이 60초 유지될 때 새 부하 측정을 시작한다. 이미 진행 중인 시험은 호스트 상태와 관계없이 원래 기준으로 판정한다. 외부 표본은 앱에 요청을 추가하지 않는다.

## 최종 후보의 기본 35 VU Soak

35 VU 활성 표본 7,200개가 7,198.98초에 걸쳐 수집됐다. 7,200초 profile에서 HTTP 142,344건(200 136,640건, 예상 409 5,704건), 동기 실행 7,047건, 동기 429·예기치 않은 오류·실행 실패는 각각 0건이었다. DB에는 exit 0으로 성공한 서로 다른 Run ID 7,047개가 있었다. 전체 p95 112.53ms, 동기 실행 p95 157.67ms·p99 188.32ms였다. 자식 프로세스 수는 1,425개 자원 표본에서 최대 2개였다. 각 phase가 끝난 뒤 남은 자식·임시 파일은 0개였다. 사전·부하·사후 스냅샷 및 원본 fixture 지문 검사가 통과했다.

같은 서버의 사전·사후 5분 읽기는 각각 754건·753건으로 모두 성공했다. 회복 조건은 사후 수치가 사전의 120% 이내인 것이다.

### 회복 후 케이스 목록

7개 읽기 엔드포인트 중 p95가 증가한 경로는 `GET /api/cases`였다(62.83→138.83ms). 기본 프로젝트 20개의 케이스 수는 2,000→6,954개였다. 런타임 검사용 고정 케이스 1개를 포함한 스냅샷 총수는 2,001→6,955개다.

사후 SQLite 투영을 그대로 두고 각 프로젝트의 기존 참조만 처리하는 경우와 쓰기 후 전체 참조를 처리하는 경우를 교차 측정했다. 실제 목록 핸들러의 `case_summaries`를 사용해 프로젝트당 1회 예열 후 3회씩, 총 60쌍을 대조했다. 기존 참조의 응답 내용은 일치했고 처리 시간 중앙값은 16.06→45.97ms였다. 이 값은 파일 경로 확인·JSON 읽기·URL 추출 시간이다. 데이터량 증가가 목록 처리 시간을 늘리는 것은 재현됐고, 전체 CPU 차이에 대한 기여도는 따로 측정할 항목이다.

## 자동 회귀

최종 후보에서 실제 테스트 PostgreSQL·Redis를 포함한 Python 724개가 139.210초에 통과했다. 프런트엔드 169개(38파일, worker 2개), production build, OpenAPI 서버 생성 및 LT-5 보고서 최신성, k6 모델 5개도 통과했다. build에는 기존 번들 크기 경고가 있었다. Windows 실기기 검증은 사용자 요청으로 보류했다.

병합 후 빈 Workspace에서 기존 접수 회귀가 기본 파이프라인에 의존하는 문제가 드러났다. 테스트마다 임시 DB·프로젝트 경로를 배정하고 명시적 inline 케이스로 검증하도록 고쳤다. 이 테스트 fixture를 포함한 전체 Python 724개도 101.135초에 통과했다. 성능 측정 대상 제품 소스는 `b83e3f5`다.

## 재현

프로젝트 가상환경에서 같은 버전의 k6 경로를 지정한다. 각 출력 디렉터리는 새 경로여야 한다.

```sh
python -m api_test.load_test_harness generate --dataset medium --root <fixture>
python -m api_test.load_test_harness target --fixture <fixture> --output <새-target-출력> --k6 <k6>
python -m api_test.load_test_harness soak --fixture <fixture> --output <새-soak-출력> --k6 <k6>
python -m api_test.load_test_harness verify --root <fixture>
```

Target은 별도 출력을 써서 3회 실행한다. 위 명령은 기본 시간을 사용한다. 동기 실행 수는 k6의 `POST /api/run` 상태별 원본, SQLite 저장 이력과 고유 Run ID에서 각각 대조한다.

원시 JSONL·서버 자원·실행 이력 대조 자료는 로컬 `data/load-test-evidence/sync-run-admission-20261107/`에 후보별로 보존했다. 98개 입력 파일을 압축 자료와 대조했고 63개 파일 지문을 다시 확인했다. 상위 색인 SHA-256은 `08b05593c0e4c028ed0e7f4a58fd9ee784654c9cee050e23fb61d9e5c7ec0ef1`이다.
