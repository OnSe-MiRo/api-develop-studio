# P1 동일 조건 기준선과 회복 진단

2026-10-04에 격리된 Medium SQLite fixture와 한 macOS 호스트에서 읽기 5 VU·300초를 같은 서버에서 세 번 직렬 실행했다. 세 실행은 각 756요청, 오류·실패 check 0건, `/api/cases` trace 108건, 자식 프로세스·임시 파일 잔여 0건이었다. 원본 fixture와 28개 측정 대상 소스, k6 binary, 환경 조건을 실행 전후 비교했다. 독립 원시 데이터 재계산 결과도 저장된 요청 수·RPS·p95·자원 집계 및 SHA-256과 일치했다. 실행별 중앙값은 **2.437879 RPS, p95 30.8635 ms**다. [전체 실행 증거](p1-baseline-evidence.json), [재생성 보고서](p1-baseline-report.md), [검증 색인](p1-validation.json)에 판정과 원본 식별자가 있다.

별도 회복 진단의 전후 읽기를 포함하면 정규 300초 구간은 총 5개, HTTP 요청은 3,780건, case 목록 trace는 540건이다. 이는 각 명령의 25초 준비 실행과 async job 접수·조회 요청을 제외한 합계다. 결과 JSON의 `commitSha`는 분기 기준 커밋 `40a852f`를 가리킨다. P1 진단 소스는 현재 미커밋 상태이므로 실제 측정 코드의 동일성은 각 파일의 `sourceSha256` 원장으로 확인한다.

| 실행 | RPS | HTTP p95 (ms) | 서버 CPU (%) | k6 CPU (%) |
| --- | ---: | ---: | ---: | ---: |
| 1 | 2.437879 | 30.28250 | 0.1803 | 0.1264 |
| 2 | 2.437863 | 30.86350 | 0.1881 | 0.1324 |
| 3 | 2.437929 | 36.12325 | 0.2294 | 0.1384 |

서버와 k6 CPU는 각각 관측 가능한 process tree의 표본을 호스트 논리 CPU 8개로 나눈 값이다. 서로 같은 process의 사용량이 아니며 장치 IOPS·latency, 종료 사이 자식 CPU, 호스트 전체 CPU는 수집하지 않았다. 1~3초 think time이 포함된 현재 RPS는 최대 처리량 측정값이 아니다.

| `/api/cases` handler 내부 평균 (ms) | 실행 1 | 실행 2 | 실행 3 |
| --- | ---: | ---: | ---: |
| 전체 계측 구간 | 27.571 | 28.880 | 31.601 |
| projection 파일 읽기 | 12.026 | 13.684 | 13.784 |
| 경로 확인 | 7.824 | 7.686 | 9.047 |
| JSON 파싱 | 4.338 | 4.217 | 5.070 |
| store 조회 | 2.870 | 2.780 | 3.100 |

store 조회에는 연결·잠금·SQL 실행·row 반환이 함께 들어 있다. 이 구간은 SQL 시간만 뜻하지 않는다. 파일 읽기와 경로 확인은 이 handler 내부에서 큰 구간으로 관측됐지만, trace 쓰기·ASGI 전송·네트워크·클라이언트 시간은 빠져 있다. 따라서 이 평균을 HTTP p95에 더하거나 기존 LT-2 단일 fresh-server 측정보다 개선됐다고 결론 내릴 수 없다. 원인 분리 후에만 목록 query나 projection 읽기 방식을 조정한다.

별도 같은 서버 회복 진단은 300초 사전 기준선 → async job 5건씩 두 배치 → 300초 사후 기준선으로 실행했다. 10건 모두 terminal passed이고 배치 후 자식·임시 파일 잔여는 0건이었다. p95는 **29.35825→31.466 ms**(1.0718배)로 120% 조건을 통과했다. 서버 CPU·RSS·thread·handle 및 오류율의 같은 기준도 통과했다. `studio-run-0/1`의 native ID는 유지됐고 관측된 AnyIO thread 수는 3/2/2/1로 바뀌었다. `ps`의 사전·사후 thread 수는 6→4이며 Python 이름별 census와 별도 측정이다. [전체 회복 증거](p1-recovery-evidence.json)와 [재생성 보고서](p1-recovery-report.md)에 실행별 자원 창과 결과가 있다.

이번 통과는 사전 준비된 worker를 포함한 **이 로컬 조건**의 회복 증거다. 과거 P0의 회복 실패를 지우거나 lazy worker 생성이 그 실패의 단독 원인이었다고 증명하지 않는다. 최대 안정 RPS·지속 run 동시성·Target/Soak SLO와 PostgreSQL·Windows·운영 성능도 여전히 미확정이다. 다음 측정은 worker 사전 준비 여부를 통제한 반복 실험과 handler 밖 지연 계측으로 원인을 좁힌 뒤, 병목이 확인된 부분만 제품 코드에서 개선한다. 전체 잔여 개발 순서는 [개발 진행 기록](api-development-progress.md)에 유지한다.
