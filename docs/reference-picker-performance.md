# Large 규모에서의 선택기 성능

실행 대시보드가 열릴 때 프로젝트 목록에 이어 케이스와 파이프라인도 조회했다. 파이프라인 편집기는 현재 프로젝트의 모든 케이스를 select에 넣었다. 선택기에 기존 Workspace 범위 keyset API를 연결하고, 페이지 크기를 20으로 설정했다. 검색과 이전·다음 이동은 명시적으로 적용하며 다른 페이지에 있는 현재 선택은 유지한다.

## 실제 브라우저 측정

2026-11-06에 로컬 SQLite에서 Large fixture를 생성했다. 프로젝트 100개, 프로젝트당 케이스 200개, 총 20,000개, revision 1개, 파이프라인 0개다. 하네스가 검증한 fixture SHA-256과 두 빌드의 index.html SHA-256을 원시 측정에 기록했다.

| 화면 | 목록 요청 수 | 반환 참조 수 | 목록 응답 바이트 | 선택기 API 응답 중앙값 | 선택 가능 시점 중앙값 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 실행 대시보드 | 3 → 1 | 300 → 20 | 38,461 → 2,934 | 17.9 → 5.5 ms | 133.0 → 79.8 ms |
| 파이프라인 편집기 | 3 → 1 | 300 → 20 | 38,461 → 2,838 | 37.7 → 8.9 ms | 128.0 → 80.7 ms |

두 빌드를 같은 Chrome, 백엔드 프로세스, DB에서 교대로 열었다. 페이지마다 새 브라우저 컨텍스트를 사용했다. 화면당 각 빌드 1회 예열 후 5회씩 측정했다. 정적 번들만 빌드별로 선택하고 모든 API는 실제 루프백 HTTP로 호출했다. 목록 수치는 프로젝트·케이스·파이프라인 목록의 합이며, 응답 시간은 대시보드의 프로젝트 목록과 편집기의 케이스 목록 각각에 대한 브라우저 측정값이다. 선택 가능 시점은 내비게이션 시작부터 실제 옵션이 채워지고 select가 활성화된 때까지다. 바이트는 수신한 본문 크기, 행 수는 반환 참조 수다. 이 값의 적용 범위는 한 로컬 환경의 초기 화면 진입이다. [24회 원시 측정](reference-picker-large.json)

대시보드에서 다음 페이지 프로젝트 선택 → 100번째 프로젝트 검색 → 새로고침 복원을 확인했다. 편집기에서는 다음 페이지의 케이스를 선택한 후 200번째 케이스를 검색해 실제 파이프라인 단계에 추가했다. 이 흐름의 전체 목록 요청과 브라우저 예외는 각각 0건이었다.

## 재현 조건

`python -m api_test.load_test_harness generate --root <새-경로> --dataset large`로 fixture를 생성한 후 하네스의 로컬 서버를 시작한다. 비교 기준은 커밋 `48459f7`의 web production build다. 비교할 두 빌드와 서버의 ready 파일을 준비해 아래 명령을 사용한다. Playwright와 로컬 Chrome 실행 경로는 테스트 환경에 맞춰 지정한다.

```sh
PLAYWRIGHT_MODULE=<playwright-모듈> BROWSER_BIN=<Chrome-실행파일> node scripts/benchmark_reference_pickers.cjs <ready.json> <fixture.json> <기준-dist> <비교-dist> <결과.json>
```

케이스 내보내기, 빠른 호출, API 작성 사이드바도 같은 페이지 선택기를 사용한다. 부하 대시보드의 자유 입력은 검색어에 맞는 첫 20개 프로젝트와 현재 이력의 참조를 제안한다. 새 문서 저장 시 이름 충돌 확인은 별도 작업 경로다.
